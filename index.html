Data Persistence & Architecture (The 6-Layer Flow)

Durability & WAL
[Browser UI] ──► [FastAPI ASGI] ──► [SQLAlchemy Core] ──► [Connection Pool] ──► [PyMySQL] ──► [MySQL InnoDB Disk]
1

1. Presentation Layer (Browser)

User performs an action (e.g. creating a case). Client state in browser memory triggers an asynchronous fetch() HTTP request.

2

2. Application API Layer (FastAPI)

Asynchronous ASGI router validates the payload against Pydantic schemas, verifies authentication token from cookie/header, and checks RBAC permissions.

3

3. Abstraction Layer (SQLAlchemy Core)

Translates the operation into parameterized SQL statements with bind variables (:param), providing 100% immunity against SQL injection.

4

4. Connection Pool (QueuePool)

Checks out a pre-warmed connection and executes session context injection: SET @app_investigator_id = :uid, @app_client_ip = :ip.

5

5. Driver Layer (PyMySQL)

Serializes SQL commands into MySQL binary protocol packets over TCP/IP socket connection.

6

6. Storage Layer (MySQL InnoDB Disk)

Executes inside transaction context (START TRANSACTION). Evaluates constraints and BEFORE triggers, writes to the Write-Ahead Redo Log (WAL), executes AFTER triggers, and flushes to tablespaces (.ibd files) on COMMIT.

🛡️ The Server Restart Durability Guarantee

If the FastAPI server process is killed (Ctrl+C), all Python memory/RAM is completely erased. However, because transactions were flushed to persistent MySQL InnoDB tablespaces on disk, 100% of cases, evidence records, and audit logs remain intact. When FastAPI restarts, it reconnects to MySQL and serves the exact same persistent data.

Candidate Key DBMS & SQL A column capable of being the primary key. A minimal superkey. case_code is a candidate key declared with a UNIQUE constraint in cases.
Composite Key DBMS & SQL A key made of two or more columns combined together. UNIQUE(case_id, investigator_id) in case_assignments forms a composite identifier.
Surrogate Key DBMS & SQL An artificial counter number used as a primary key. An auto-incrementing integer identifier with no intrinsic business meaning (case_id).

Viva Voce Preparation Suite (Core Q&A)

Examiner Questions

Click on any question to inspect the simple explanation, academic depth, and strategic counter-answer.

Q1. Why use database triggers instead of application logging in Python? ▾

Simple Answer: Python logs only work when someone clicks a button on the website. If a hacker or rogue employee connects directly to MySQL Workbench or command line, Python never runs! Triggers live directly inside MySQL, so they catch every change no matter where it comes from.

Academic / Technical Answer: Application-level logging violates the principle of defense-in-depth and fails to guarantee non-repudiation against privileged insiders. MySQL triggers (AFTER INSERT/UPDATE/DELETE ON table FOR EACH ROW) execute synchronously within the database engine's ACID transaction boundary, having direct access to OLD and NEW pseudo-records before write-ahead log flushing.

Viva Strategy Tip: Emphasize that triggers enforce security at the data tier, making tampering impossible to hide even if the application layer is completely bypassed.

Q2. How does this project satisfy Third Normal Form (3NF)? ▾

Simple Answer: We don't store repeated information. For example, we do not store the person currently holding a piece of evidence inside the evidence table; instead, a calculation function figures it out from the transfer history table.

Academic / Technical Answer: A relation is in 3NF if it is in 2NF and contains no transitive functional dependencies (where a non-prime attribute determines another non-prime attribute). In our schema: 1) Attributes contain atomic values (1NF); 2) All non-key attributes are fully functionally dependent on primary keys (2NF); 3) Transitive dependencies are eliminated (3NF). For example, current_custodian is derived dynamically via stored function fn_current_custodian(eid) querying custody_transfers, eliminating update anomalies.

Q3. How do you prevent SQL Injection? ▾

Simple Answer: We never stick user text directly into SQL commands using plus signs or string formatting. We use special placeholders so the database knows user text is just harmless data, not executable code.

Academic / Technical Answer: All database operations execute through SQLAlchemy Core utilizing parameterized bind parameters (:param). Parameterization separates SQL syntax compilation from data literal evaluation at the MySQL protocol layer, rendering injection payloads syntactically inert.

Q4. How does SHA-256 detect file tampering? ▾

Simple Answer: SHA-256 is like a mathematical wax seal. If someone changes even a single letter, comma, or space in the file, the entire seal breaks and produces a completely unrecognizable new code.

Academic / Technical Answer: SHA-256 is a deterministic, collision-resistant cryptographic hash function defined in NIST FIPS 180-4. Due to the strict Avalanche Effect, modifying even a single bit in an evidence file flips approximately 50% of the 256 output bits. When the verification engine recalculates the hash, comparing it against the sealed original_hash mathematically proves whether the file has been altered.

Q5. What happens if an attacker tries to run DELETE FROM audit_logs;? ▾

Simple Answer: MySQL immediately rejects the command and throws an error saying that the audit history cannot be deleted or changed.

Academic / Technical Answer: The BEFORE DELETE trigger trg_audit_bd intercepts the statement and executes SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Audit history is append-only'. This forces the transaction to roll back immediately, preserving the WORM (Write Once, Read Many) integrity of the forensic trail.
